[appendix]
[#from-xstate-to-cpp]
== From XState to {cpp}

This appendix is for a reader who knows XState. It shows how each of
XState's JavaScript spellings is written in {cpp}: a machine's config, the
functions the config holds, an event, an actor, a promise and an error. The
machine itself does not change: its states, its transitions and what they
mean are XState's. What changes is how a program writes them, because {cpp}
has no object literal, a JSON config holds no function, and xstate throws
nothing.

Each section gives XState's spelling first, in inline code, a table or a
program, and then xstate's, from an example program of this page. A program
of XState's shown here is the twin of the {cpp} program after it: the same
program, which ran on XState 5.33.2 and printed what the {cpp} program
prints (<<overview-twins>>). The last section, <<reference-xstate-names>>,
goes from each of XState's names to xstate's.

Names keep XState's words, in snake case: `createMachine` is
`create_machine`, `getNextSnapshot` is `get_next_snapshot`, and
`snapshot.hasTag` is `snapshot.has_tag`. The {cpp} examples write
`namespace xstate = webcpp::xstate;`, and every value a machine holds, its
config, its context, an event's payload, an action's params, an input and
an output, is a `boost::json::value`.

[#syntax-config]
=== A JavaScript object becomes a JSON config

XState's `createMachine` takes the config as a JavaScript object, written in
the program. xstate's `create_machine` takes the same config as JSON, a
`boost::json::value` the program parses from text, reads from a file or
receives in a request. {cpp} has no object literal to write a config in, and
as data a config can come from anywhere, Stately Studio's export included,
and needs no compiler (<<rationale-json>>).

----

and JSON in xstate:

[source]
----

Every member keeps its name and its meaning; JSON changes how it is
written, and a function becomes a name:

[cols="1,1",options="header"]
|===
| XState's object | xstate's JSON

| `id: 'toggle'`, a bare key and a string in single quotes
| `"id": "toggle"`, every key and every string in double quotes

| `+after: { 2000: 'Inactive' }+`
| `+"after": {"2000": "Inactive"}+`: a key is always a string

| `+entry: assign(...)+`, `+guard: ({ context }) => ...+`
| `"entry": "incrementCount"`, `"guard": "countBelowMax"`: a name, and the
function registered under it (<<syntax-implementations>>)

| `+{ type: 'notify', params: { level: 2 } }+`
| `+{"type": "notify", "params": {"level": 2}}+`, its params fixed in the
config

| `not('isEmpty')`, `stateIn('#light.green')`
| `+{"type": "xstate.not", "guards": ["isEmpty"]}+`,
`+{"type": "xstate.stateIn", "stateValue": "#light.green"}+`
(<<transitions-higher-order>>)

| a member that is `undefined`
| the member left out (<<differences-undefined,`undefined` in JSON>>)
|===

The rules:

* `create_machine` returns a `result<machine>`: the machine, or the reason
  the config was refused, which the program tests where a program of
  XState's would catch what `createMachine` throws (<<syntax-exceptions>>). It refuses every
  config XState refuses, and some XState accepts and fails on only later
  (<<differences-refused>>).
* The keys of `states`, `on` and `after` are read in the order JavaScript
  enumerates an object's keys, as XState reads them: a key that is an array
  index, such as `"500"`, first, by number, then the rest as written
  (<<machines-config>>).
* A machine never changes once created. XState's `machine.provide()` is the
  same config created again with other implementations
  (<<machines-immutable>>), and `machine.toJSON()` is `to_json(machine)`,
  which `create_machine_from_definition` loads back
  (<<machines-definition>>).
* Appendix B lists every place where a JSON config takes another form than
  XState's object, each with its reason (<<differences-json>>).

[#syntax-implementations]
=== Functions become implementations registered by name

XState's config may hold functions: an action, a guard, a delay, the logic
of an invoked actor, and the functions that compute the initial context, an
invoked child's input and a final state's output. JSON holds none, so
xstate's config names each one, and the program registers its {cpp} code
under that name in an `implementations`, which `create_machine` takes with
the config. XState already splits a machine this way when `setup()`
registers implementations and the config refers to them by name: there,
`+setup({ ... }).createMachine(config)+` becomes
`create_machine(config, implementations)`, and the config stays as it is
(<<rationale-names>>).

`implementations` has a member for each kind of function. `actions`,
`guards`, `delays` and `actors` are keyed by name, as `setup()` keys them.
The other three stand for functions XState's config holds in place, so each
is keyed by the place: `context`, one function, computes the initial context
from the input; `inputs` computes a child's input, under the id of its
invoke; and `outputs` computes a final state's output, under the id of that
state, or the machine's under the root's id. Each member is taught in
<<machines-implementations,the section on implementations>>. Each function
keeps its role in XState and takes a {cpp} shape:

[cols="1,1",options="header"]
|===
| XState | xstate

| An action creator, such as
`+assign({ count: ({ context }) => context.count + 1 })+`
| The built-in action of the same name, such as an `assign_action`, holding
a function that returns what XState's creator computes: here the members to
merge, `+boost::json::object{{"count", ...}}+` (<<actions-built-in>>)

| An action that is a plain function, such as
`+() => console.log('done')+`
| No entry: an action name `actions` does not hold is a custom action,
returned to the program, which performs it (<<actions-custom>>)

| A guard, `+({ context, event }, params) => boolean+`
| A `predicate`: a function of an `action_args`, which returns
`result<bool>`

| A delay, `+({ context, event }) => number+`
| A `delay_maker`, which returns `result<std::uint64_t>`, in milliseconds

| `src: childMachine`, `+src: fromPromise(...)+`
| A `+machine_actor{child_machine}+`, or a `host_actor{}`
(<<syntax-promises>>)

| `+context: ({ input }) => ({ ... })+`
| `implementations.context`: a `context_maker`, a function of the input that
returns `result<boost::json::value>`

| An invoke's `+input: ({ context }) => ...+`, a final state's
`+output: ({ context }) => ...+`
| A `value_maker`, in `inputs` or `outputs`, which returns
`result<std::optional<boost::json::value>>`, none for `undefined`
|===

The rules:

* Every implementation receives an `action_args`: `args.context`,
  `args.event` and `args.params`, XState's `+({ context, event }, params)+`.
  It receives no actor and no system, where XState's also receives `self`
  and `system`.
* Every implementation returns a `result`, and fails by returning an error
  where XState's would throw (<<syntax-exceptions>>).
* A name is checked when the machine is created. A guard, an `after` delay
  or an actor that the config names and `implementations` does not hold
  refuses the machine, where XState fails when it first needs the name, or
  never (<<differences-refused>>). An action name is not checked: one that
  `actions` does not hold is a custom action, by design.
* `params` are fixed in the config. Where XState computes them with a
  function of the context and the event, xstate's implementation reads the
  two from its `action_args` (<<differences-names>>).

[#syntax-events]
=== A flat event object becomes `event{type, payload}`

An event in XState is one object: its `type`, the string that names what
happened, and its data, the other members beside the type. xstate's `event`
holds the two apart: `type`, a `std::string`, and `payload`, a
`boost::json::object` holding every other member. Transitions match the
type alone, and the payload is JSON, as every value a machine holds is
(<<transitions-events>>).

  the member `output` of `args.event.payload` (<<input-output-done-events>>).
* An event carries no actor, since a payload is JSON
  (<<syntax-actor-refs>>).

[#syntax-actor-refs]
=== Actor references become `actor_ref`

XState's `createActor` returns an actor, an object whose methods start it,
send it events, read and subscribe to its snapshot, and stop it. In xstate,
actors live in an `actor_system` the program creates, and `create_actor`
returns an `actor_ref`, a number that names one actor of that system. Each
method of XState's actor becomes a member of the system that takes the
reference first: `actor.send(event)` is `system.send(actor, event)`. XState
creates a system too, implicitly, for each root actor; xstate makes it
explicit, because the system owns what the host decides: the fuel each call
may spend, the time, and the systemIds its actors share (<<actors-create>>).

The table of <<reference-xstate-names,XState's names>> gives each method of
XState's actor and the member of `actor_system` that does its work. The
rules:

* An `actor_ref` is a value, copied and compared as a number is, and keeps
  nothing alive. An address is never reused, so a reference to an actor that
  has ended still names it: `status_of` says how it ended, and an event sent
  to it is dropped, as XState drops an event sent to a stopped actor. A
  reference that names no actor of the system is refused with
  `invalid_argument` (<<webcpp-xstate-actor_ref>>).
* XState's `actor.getSnapshot()` returns a snapshot. `snapshot_of(actor)`
  returns a pointer to one, `nullptr` until the actor has started
  (<<differences-construction>>).
* XState's `actor.send` returns nothing. `system.send`, like every call that
  delivers something, runs the system and returns a `result<run_outcome>`:
  `settled`, `out_of_fuel` or an error (<<quick-start-actor>>).
* A config names an actor by a string and never holds one: a child by its
  id, the parent as `+#_parent+`, and any actor by its systemId as
  `+#system:<systemId>+` (<<differences-targets>>).
* XState's `snapshot.children` holds its children's references. xstate's
  holds their ids and srcs, and `child_of(actor, id)` returns a child's
  reference; XState's `actor.system.get(systemId)` is `system.get(systemId)`.

[#syntax-promises]
=== Promises become host actors

XState runs asynchronous work, a request to a server or a file to read, as a
promise actor: `fromPromise` makes actor logic of a function that returns a
promise, `setup({ actors })` registers it, and an invoke or a spawn starts
it. When the promise resolves, the parent receives
`xstate.done.actor.<id>` with its `output`; when it rejects,
`xstate.error.actor.<id>` with its `error`. A {cpp} library has no promise to
await, and with no event loop and no thread of its own it cannot wait for
one. So the work is the host's. A `host_actor`, registered under the actor's
name, stands for the promise: once started, it is a pending request that the
host lists with `host_requests()`, works on at its own pace, and answers with
`resolve(request, output)` or `reject(request, error)`, and the parent
receives the same events (<<actors-host>>).

registers the promise with `fromPromise`. This one does not fetch: it hands

[cols="1,1",options="header"]
|===
| XState | xstate

| `+fetchUser: fromPromise(...)+` in `setup({ actors })`
| `host_actor{}` in `implementations.actors`

| The promise function's `input`
| The request's `input`, which an invoke's `input` gives, or the function
registered under the invoke's id in `implementations.inputs`

| The promise resolves with a value

| The promise rejects with an error
| `system.reject(request, error)`

| The members `output` and `error` of `args.event.payload`

| A promise that settles after its actor has stopped is ignored
| An answer to a request no longer pending is refused with
`invalid_argument`, and changes nothing
|===

[#syntax-exceptions]
=== Exceptions become `result`

XState reports a failure by throwing. `createMachine` throws on a config it
refuses, and an implementation that throws fails the actor that runs it: the
snapshot's `status` becomes `'error'`, and its `error` is what was thrown.
xstate throws nothing, since it builds where exceptions are off
(<<rationale-no-exceptions>>). A call that can fail returns a `result<T>`,
Boost.System's `result`, which holds the value or an `error_code`. An
implementation that fails returns one,
`failure<T>(errc::implementation_failed)` or any other `error_code`, and a
machine that fails while it runs settles in a snapshot whose `status` is
`error` and whose `error` is that code (<<rationale-errors>>).

<<syntax-config,The toggle above>> already tests the `result` its
`create_machine` returned: where XState's caller would catch, xstate's tests
`has_value()` and reads `error()`.

[cols="1,1",options="header"]
|===
| XState | xstate

| `+try { createMachine(config) } catch (error) { ... }+`
| `create_machine(config, implementations)` returns a `result<machine>`; the
program tests `has_value()` and reads `error()`

| `+throw new Error('...')+` in an implementation
| `+return xstate::failure<T>(xstate::errc::implementation_failed);+`, or
any other `error_code`

| `snapshot.status === 'error'`, `snapshot.error`
| `snapshot.status == xstate::status::error`, and `snapshot.error`, an
`error_code` whose `message()` is its name, such as
`implementation_failed`

| `actor.subscribe({ error })`
| No error callback: `status_of(actor)` says the actor failed
(<<actors-watching>>)

| The `error` of `xstate.error.actor.<id>`: what the child threw
| The member `error` of `args.event.payload`: the failed child's error, or
the name of its code (<<differences-failures>>)
|===

The rules:

* A `result` is tested before it is read. `*` reads the value of a result
  that holds one, and `value()` of a failure calls `boost::throw_exception`,
  which ends a program built without exceptions (<<webcpp-xstate-result>>).
* The actor layer refuses a call it cannot take, such as one that names no
  actor, with xactor's
  link:{webcpp-libs}/xactor/{webcpp-page}#webcpp-xactor-errc-invalid_argument[`invalid_argument`],
  and changes nothing
  (<<overview-errors>>).
* Boost.JSON's accessors that check by throwing, such as `at` and
  `as_int64`, have counterparts that answer instead: `if_contains` and
  `if_int64` with a pointer, `try_at` and `try_as_int64` with a `result`
  (<<quick-start-context>>).
