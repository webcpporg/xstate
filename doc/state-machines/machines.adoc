[#machines]
== Machines

A state machine describes how something behaves: the states it can be in,
and the event that takes it from one state to another. A machine is the
logic of an actor, not the actor itself. It holds no current state: the
state it is in lives in a snapshot, and a running instance of it is an
actor. Any number of snapshots and actors are made from one machine, each
independent of the others.

A machine is built from two things: a config, the description XState's
`createMachine(config)` takes, and implementations, the code the config
names. xstate reads the config as JSON and takes the implementations by
name. This section shows how a machine is created, what its config holds,
how implementations are registered and why by name, why a machine never
changes, what creation refuses, how to find a state node, and how a machine
is written out as XState's definition and loaded back.

[#machines-creating]

cursor they are built on. Stately's page runs the machine as an actor, with
`createActor`; in xstate an `actor_system` does that, as <<actors,Actors>>
shows.

[#machines-config]
=== The config

A config describes the machine: its states, the transitions between them,
the actions they run, its context. In xstate it is the object XState's
`createMachine` takes, written as JSON. JSON holds data only, where XState's
config, a JavaScript object, may also hold functions: an inline action, a
guard written as an arrow function, a context computed from the input. That
is a choice, for three reasons:

* A config is data a person writes, or exports from Stately Studio, and a
  program loads at run time, from a file, a database or a request, with
  nothing to compile.
* The JSON is XState's config: xstate's tests run their configs on XState
  itself and compare the two, one microstep at a time
  (<<testing,Testing>>). Only XState's higher-order guards, functions
  there, take a JSON form of xstate's
  (<<transitions-higher-order,Higher-order guards and stateIn>>).
* {cpp} has no object literal that holds functions. A config holding {cpp}
  code would be {cpp} code too, compiled into the program.

What a function does in XState's config, a name does in xstate's: the
config names the function, and the implementations hold it
(<<machines-implementations,Implementations>>). An action or a guard is
named as XState's JSON writes it, `"entry": "notify"`, or
`+{"type": "notify", "params": {...}}+` with fixed `params`, which the
implementation reads from its `action_args` together with the context and
the event. A higher-order guard is a JSON object,
`+{"type": "xstate.not", "guards": [...]}+` and the like.
Appendix A maps each function XState's config may hold to its form in
xstate (<<syntax-implementations>>), and <<differences-names>> gives the
three that cannot keep what they do in XState.

The members xstate reads, on any state unless the table says otherwise:

A transition is a target, an object (`target`, `actions`, `guard`,
`reenter`, `description`, `meta`) or a list of them
(<<transitions,Events and transitions>>). A target names a sibling of the
transition's state by its key, or a state below that sibling by a path of
keys joined by dots, `"red.stop"`; a state below the transition's own state
by a path that starts with a dot, `".child"`; or any state by its id,
`"#id"` (<<transitions-targets>>). `states`, `on` and `after` are read in
the order JavaScript enumerates an object's keys, as XState reads them: a
key that is an array index, such as `"500"`, first, by number, then the
rest as written (<<machines-nodes>>).

xstate reads no other member of a transition but `cond`, XState v4's name
for `guard`: a truthy `cond` refuses the machine, as XState's development
build refuses it (<<machines-refusals,What creation refuses>>). `types`,
which only TypeScript reads, and `schemas`, which XState keeps on the
machine without using, are left unread. So is `options`: XState uses its
`maxIterations` to throw on a macrostep that never settles, and in xstate
the bound is the fuel of the caller that drives the cursor
(<<pure-cursor-fuel,Fuel>>). So is XState's `route`, which lets the event
`+{"type": "xstate.route", "to": "#<id>"}+` reach, from any state, a state
that has an `id` and a `route`; in xstate that event selects no transition.

[#machines-implementations]
=== Implementations

Implementations are the code a machine runs that is not its states and
transitions: actions, the side effects; guards, the conditions a transition
is taken on; delays, the time before a delayed transition; and actors, what
a state invokes. Three more compute a value: the initial context from the
input, an invoked child's input, and a final state's output.

`implementations` holds them by name, as XState's
`setup({ actions, guards, delays, actors })` registers them, so that the
config refers to each with a string. In xstate a name is the only way,
because a JSON config holds nothing else, and registering by name gives
three things:

* The config stays data, XState's own, and `to_json` writes the machine
  back as XState's definition (<<machines-definition,The definition>>).
* One config runs with different implementations
  (<<machines-immutable,A machine is immutable>>).
* Creation checks the names the config uses: a guard, an `after` delay or
  an actor the implementations do not hold refuses the machine
  (<<machines-refusals,What creation refuses>>), where XState fails only
  when it first needs the name, or never (<<differences-refused>>). A delay
  that an action implementation names in its `delay` is not checked: one
  that is not registered means no delay, as in XState.

An action is the exception: an action name the implementations do not hold
is not an error. It is a custom action, which xstate returns to its caller
to execute, as XState's `transition` returns it
(<<actions-custom,Custom actions>>). That is how a caller's own effects, a
log line, a request, a write, reach it.

reads before it reads it, as `add` does, and returns `implementation_failed`
when the context is not what it expects.

<<actions-built-in>> lists the built-in actions, each with what the core
returns for it. The machine core runs no actor itself: entering a state
that invokes one resolves into an `xstate.spawnChild` action and leaving it
into an `xstate.stopChild`, an invoke's `onDone` and `onError` are
transitions on `xstate.done.actor.<id>` and `xstate.error.actor.<id>`, and
the actor layer runs the child and delivers those events
(<<actors-invoke>>).

The context's function receives the input. Every other function the
implementations hold receives an `action_args`: the context as it is when
the function runs, the event of the microstep, and the `params` the config
gave the action or the guard, null when it gave none. The root's output is
the one exception to the event: it receives the done event that completed
the machine, as XState's does. For a compound root, that is the done event
of the top-level final state, which carries that state's output; for a
parallel root, it is the root's own done event, which carries none
(<<input-output-machine-output-event,The machine's output and its final
state>>). Each function returns a `result`, and an error it returns stops
the macrostep, which leaves the snapshot it began from with the status
`error`, where XState's implementation would have thrown
(<<differences-failures>>).

Three rules hold for the implementations, each checked at creation:

* An implementation holding an empty function, a default-constructed
  `std::function`, refuses the machine with `invalid_config`: calling it
  would abort in a build without exceptions. An optional function
  left out holds none: a `log_action` without a `value` is a log of the
  context and the event, as in XState.
* An `inputs` entry names an invoke whose config gives no `input`, and an
  `outputs` entry a final state, or the root, whose config gives no
  `output`; any other is `invalid_config`.
* Every actor the config names, by an invoke's `src` or through a
  `spawn_child_action` it names as an action, is an entry of `actors`; any
  other is `unknown_actor`. A registered `spawn_child_action` the config
  never names is not checked, as XState's `setup` accepts it.

[#machines-immutable]
=== A machine is immutable

A machine never changes once it is created. The state it is in lives in a
snapshot, a value of its own, so one machine serves any number of snapshots
and actors at once, and nothing one of them does reaches another. A
`machine` is a handle to data its copies share: copying one copies a
pointer, not the tree, so a cursor, an actor or a `machine_actor` keeps a
copy. The transitions a microstep reports point into the machine, and stay
valid while any copy of it lives.

To run one config with other implementations, create a second machine from
it. `create_machine` takes the whole set of implementations, so a program
that changes some of them copies the first machine's, `registry()`, and
replaces the entries that change. XState's `machine.provide` does this in
one call; xstate has no `provide` (<<overview-not-ported>>).

[#machines-refusals]
=== What creation refuses

A config is checked once, when the machine is created, and a config that is
not a machine gives no machine: `create_machine` returns the error instead.
Every machine comes from `create_machine`, which
`create_machine_from_definition` calls too, so a machine that exists has
passed every check, and a mistake in a config shows when the config is
loaded, not when an event first reaches it.

The error is a value, not an exception. xstate throws no exception of its
own, and builds with exceptions turned off, as this page's examples are
built for wasm32-wasip2; where XState throws, xstate returns an error.
`result<T>` is
`boost::system::result<T, boost::system::error_code>`; its error is a code
of the category `webcpp.xstate`, one of the values of `errc`, and
`message()` spells its name. Check `has_value()` before using a result.

| `invalid_config`

  runs with the null tag, and fails when it runs the null action

| Has a compound state without `initial`

| `invalid_config`
| No counterpart: these are functions in XState

| Names a guard the implementations do not hold
| `unknown_guard`
| Throws when the guard is evaluated

| Has an `after` key that is not digits alone but starts with a digit, a

| `invalid_config`

Some members hold any value, as in XState: a state's `meta`, the root's
`version`, the `output` of a final state or of the root, and a transition's
`meta` and `description`. Two values are dropped, where XState keeps them:
a state's `meta` that is null, which xstate reads as no meta, and a state's
`description` that is not a string, an exception to the first row.

One config is accepted as XState accepts it: a machine whose root is itself
a history state, which has no parent to resolve its default target against.
A microstep that needs that default fails with `unknown_target`, where
XState throws (<<states-history,History states>>).

What creation cannot see fails later, and as a value too: an
implementation that returns an error fails the microstep that calls it, and
the snapshot it leaves has the status `error` (<<actions,Actions>>).

[#machines-nodes]
=== State nodes and ids

A machine is a tree of state nodes, one for the root and one for each state
of its config, and a node holds everything the config says of its state.
A program reads the nodes to show a machine, to name a state in a target or
a query, or to read what a snapshot's active states are.

xstate keeps the nodes in one list, in document order: the root first, a
parent before its children, and the children in the order JavaScript
enumerates the keys of `states`, as XState reads them. A key that is an
array index, such as `"0"` or `"2"`, comes first, by number, and the others
follow as the config writes them: the children `b`, `10` and `2` are listed
`2`, `10`, `b`. A node is named by its index in that list, so the tree
holds no pointer: `size()` is the number of nodes, `node(index)` one of
them, for an `index` below `size()`, and `root()` is `node(0)`.

A `state_node` holds what XState's `StateNode` holds once it is
initialised: its `key` in its parent's `states`, its `id`, its `path` of keys
from the root, its `type`, the index of its `parent`, its children, its
entry and exit actions, its transitions and invokes, its tags, meta, output
and description. A state's id is the `id` its config gives, or, without one,
the machine's id and the state's path, joined by dots; the machine's id,
`id()`, is the root's `id`, `(machine)` when the config gives none, as in
XState. An explicit id names its own node only: below, the children of
`playing`, whose id is `active`, are `player.playing.normal` and
`player.playing.fast`.

nodes of the machine share an id. Three functions find a node, each
returning its index as a `result<std::size_t>`:

* `node_by_id(id)` is XState's `getStateNodeById`. The `#` is optional, and
  a path after the id walks down from that node: `#active.fast` is the child
  `fast` of the node whose id is `active`.
* `child(node, key)` is the child of `node` whose key is `key`, a dot being
  part of the key.
* `node_by_path(from, path)` is XState's `getStateNodeByPath`: a path of
  keys relative to `from`, or an id when it starts with `#`.

A backslash escapes a dot in an id or a path: `#foo\.bar` names the node
whose id is `foo.bar`, where `#foo.bar` names the child `bar` of the node
`foo`. A name that finds no node is the error `unknown_state`, where
XState's `getStateNodeById` throws.

The machine also keeps what it was created from: `config()` is the config,
`registry()` the implementations, and `context()` the config's `context`, an
empty object when the config gives none or null. The reference lists every
member of `machine` (<<webcpp-xstate-machine>>).

[#machines-definition]
=== The definition

A machine's definition is the machine written out as JSON, once its config
has been read: every node with its id, key, type, initial transition and
children, its transitions with their targets resolved to lists of `#id`,
its entry and exit actions, its `order` (the root's is written `-1`), its
invokes and its tags. It is what a program stores, sends or hands to a tool
when it needs the machine as data, every target already resolved. XState
writes it with `machine.toJSON()`, which `JSON.stringify(machine)` calls,
and `to_json(machine)` writes the same definition:

definition key for key, with two exceptions. It leaves out the two values

refuses>>). And it adds the higher-order guards, which XState cannot write:
they are functions in XState, and `JSON.stringify` leaves a function out.
The members of an object may come in another order than XState's, so
compare two definitions as JSON values, with `==`, and not as text.

The reloaded machine takes the original's step, starts from the context it
was given, and writes the definition it was loaded from, the toggle's
`version` on every node included. XState has no function that creates a
machine from a definition.

The loader refuses with `invalid_config` what XState never writes: a value
that is not an object, and a state whose `states`, `on`, `invoke`, `entry`
or `exit` does not have the JSON type a definition gives it, an object of
state objects, an object of lists of transition objects, a list of invoke
objects, a list of actions; and, in a state that has `states`, an `initial`
whose first target is not a string. From any other object it rebuilds the
config the definition describes and creates the machine with
`create_machine`, which checks it as it checks any config
(<<machines-refusals,What creation refuses>>): an `id` that is not a
string, or a `type` xstate does not know, is `invalid_config` there. So is
an `entry`, `exit`, `actions` or `tags` list that holds null, the list
XState writes for one of them that is null, which creation refuses in a
config too. A compound state's `initial` is rebuilt from its first target,
`#` and the id of a child, with the `actions`, `meta` and `description` of
the written initial transition; a target that names none of the children
leaves the state without an `initial`, which is `invalid_config` too, where
a config's `initial` that names no child is `unknown_target`.

Three members repeat what the rest of the definition says and are not
read, whatever they hold: `key`, `order` and `transitions`; nor is the
`version` of a state below the root, which repeats the root's. The root's
`version` becomes the machine's, which `to_json` writes on every node
again.

A definition does not hold all of a config either. The definition, XState's
and so the one `to_json` writes, leaves out the context, the eventless
transitions (`always`) and a history state's default target; two states may
share an id when a key holds a dot; and an entry or exit action named
`xstate.raise` or `xstate.cancel`, a custom action, cannot be told from the
raise and cancel an `after` adds, which the definition writes under those
names, so the loader drops it with them. Given the original's context, a
machine loaded from a definition takes the original's steps and writes the
same definition whenever the original has none of those; one loaded from a
definition XState wrote writes it without the two values `to_json` leaves
out. A definition XState wrote has no higher-order guard either: the
transition comes back unguarded, and the reloaded machine takes it whatever
the guard would have decided. One `to_json` wrote keeps the guard.
