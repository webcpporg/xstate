[#input-output]
== Input and output

_Input_ is the data an actor is given when it is created. _Output_ is the data
an actor produces when it is done: the result of its work. Between the two sit
the _done events_, which tell a state or a parent actor that what it waited on
has finished, and carry the output to it.

Input exists so that one machine can start from different data: a feedback form
for one user or another, a conversion of one amount or another. Without it, each
starting value needs a machine of its own, built by a factory function. Output
exists so that whoever waits on an actor receives its result without reading the
actor's context.

In xstate, as in XState, input and output are values, here JSON values. A value
that depends on nothing stays in the config, where XState's JSON puts it. A
value XState computes with a function (a context from the input, an invoke's
input from the context, an output from the context) needs a function JSON cannot
hold, so the caller registers it in `implementations`, as it registers actions
and guards (<<machines-implementations,Implementations>>).

An invoke's computed input and a state's computed output are registered under
the id of the invoke or the state, and not under a name the config refers to, as
an action is. In XState's JSON an invoke's `input` and a state's `output` are
the values themselves: a string there is the input, not the name of a function.
Keyed by id, the function leaves the config as XState reads it.

[#input-output-init-event]
==== The `xstate.init` event

A machine's initial macrostep runs for the event `xstate.init`. When the machine
has an input, the event carries it as its member `input`, so every action that
runs for `xstate.init` can read it from the event: the entry actions and initial
actions of the states the machine starts in, as this entry action does, and the
eventless transitions taken before any raised event, with the entry actions of
the states they enter. An action that runs for an event raised during the
initial macrostep, a done event among them, receives that event, which has no
`input`.

Where XState writes the entry action as a function of the event,
`+({ event }) => ...+`, here it is a named `log_action` whose value is the
event, read from its `action_args`; the actor system hands each value logged
to its `on_log` listener (<<actions-log,Log>>).

[#input-output-invoke-input]

[#input-output-spawn-input]
=== Input to a spawned actor

A child spawned by an action receives its input from the action. XState's
`spawnChild(src, { id, input })` is a `spawn_child_action` registered under a
name, whose `input` is a `value_maker` computed when the action resolves, from
the context and the event of its microstep. Without one, the child has no input;
a fixed input is a function that returns it.

context. xstate has no `spawn` inside `assign`, and an actor reference is not

[#input-output-output]
=== Output

A machine's output is the value it is done with. It is the output of its root,
computed when the machine is done, when a top-level final state is entered or
each region of a parallel root is in a final state
(<<states-done,When the machine is done>>), and from then on it is the
snapshot's `output`, a `std::optional<boost::json::value>` that holds nothing
while the machine is active. The root's output is fixed in the config, the
root's `"output"`, or computed: XState's `+output: ({ context }) => ...+` at the
root of the config is a `value_maker` registered in `implementations.outputs`
under the root's id.

[#input-output-undefined]
==== When a value is undefined

JavaScript has `undefined`, and JSON has not. A `value_maker` returns
`std::optional<boost::json::value>`: none stands for `undefined`, and the member
that would hold it is left out, as JavaScript's `JSON.stringify` leaves it out.
The snapshot then has no output, a done event no `output`, a child no input
(`host_request::input` holds nothing, and the `xstate.spawnChild` params have no
`input`), a log no value.

A JSON `null` is a value like any other, and is kept: a `null` output, a done
event's `null` output, a host actor's `null` input. The exception is a machine's
input: for a machine, a null input and no input are the same, and its
`xstate.init` has no `input` (<<input-output-init-event>>,
<<differences-undefined,`undefined`>>).

[#input-output-done-events]
=== Done events

When something a machine waits on finishes, the machine hears it as an event,
and `onDone` is the transition that takes it. A done event lets a parent move on
when what it started has finished, without knowing the steps that finished it:
the coffee machine's `preparation` moves to `brewing` once its steps reach
`ready`, and the order below moves on once the child that prices it is done.
There are two kinds:

[cols="2,3,3",options="header"]
|===
| Event | Raised or sent when | Members besides `type`

| `xstate.done.state.<id>`
| the state `<id>` is done: a final child of a compound state is entered, or
each region of a parallel state is in a final state
| `output`, the final child's output, when it has one; none for a parallel
state

| `xstate.done.actor.<id>`
| the child actor whose id is `<id>`, invoked or spawned, is done
| `output`, the child's output, when it has one; `actorId`, the child's id
|===

A state's `onDone` is its transition on `xstate.done.state.<state id>`. An
invoke's `onDone` is a transition of the invoking state on
`xstate.done.actor.<invoke id>`, and its `onError` one on
`xstate.error.actor.<invoke id>`, the event a child that fails sends with its
`error` and its `actorId` (<<actors-done-error,Done and error events>>). One
state can have both kinds of `onDone`: its own, for its final child, and its
invoke's, for its child actor. A spawned child has no invoke to hold an
`onDone`; its parent takes the child's done event with a transition like any
other, `+"on": {"xstate.done.actor.<id>": ...}+`.

[#input-output-rules]
=== Rules

Creating a machine checks what `implementations.inputs` and
`implementations.outputs` name, and refuses, with `invalid_config`, what could
never be called or would contradict the config: an input that names no invoke,
an input for an invoke whose config fixes one too, an output that names neither
a final state nor the root, and an output for a state whose config fixes one too
(<<machines-refusals,What creation refuses>>). XState has nothing of the kind to
check, since its functions sit in the config where they apply. An empty
`std::function`, in `implementations.inputs`, `implementations.outputs`,
`implementations.context` or the `input` of a `spawn_child_action`, is refused
with `invalid_config` too, because calling it would abort in a build without
exceptions.

the microstep that called it, as any implementation does: the macrostep settles
with the snapshot it began from, its status `error` and its `error` the
function's (<<pure-cursor-failure,When an implementation fails>>). One that
returns none leaves its member out (<<input-output-undefined>>).

[#input-output-cheatsheet]
=== Input and output cheatsheet

[cols="1,1,1",options="header"]
|===
| XState | xstate, fixed | xstate, computed

| `createActor(machine, { input })`
| `+create_actor(machine, {.input = ...})+`
|

| `initialTransition(machine, input)`
| `initial_transition(machine, input)`, `begin_initial(machine, input)`
|

| `+context: ({ input }) => ...+`
| the config's `"context"`, which does not read the input
| `implementations.context`

| `event.input` in the initial macrostep
| `args.event.payload.if_contains("input")`
|

| `invoke: { input }`
| the invoke's `"input"`
| `implementations.inputs`, under the invoke's id

| `spawnChild(src, { id, input })`
|
| `spawn_child_action::input`

| a final state's `output`
| the final state's `"output"`
| `implementations.outputs`, under the state's id

| the machine's `output`
| the root's `"output"`
| `implementations.outputs`, under the root's id

| `snapshot.output`
| `snapshot::output`, none for `undefined`
|

| `event.output` in `onDone`
| `args.event.payload.if_contains("output")`
|
|===
